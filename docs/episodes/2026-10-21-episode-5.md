The cure restored speed **without any change of carrier, cell or signal**: the same NR cell was re-added. This is the cleanest support for
M1 so far (the fault is in the NR leg's user-plane context, not in the radio). Massive reordering only in the episode fits a split
bearer delivering part of the data late.

## Episode tests (first run during an episode; reference from the good state 2026-10-21 00:03)
| | episode | good-state reference |
|---|---|---|
| ping loss 56 / 1000 / 1200 / 1400 / 1472 B, DNA | 0 / 3 / 2 / 5 / **9 %** | 0 at all sizes |
| same, Cloudflare | 0 / 2 / 3 / 7 / **7 %** | 0 at all sizes |
| DNA download, MSS default / 1200 / 1000 / default | 1.48 / 1.30 / 1.15 / 1.37 Mbit/s | 45 / 53 / 31 / 58 Mbit/s |
| pcap | 1.8 MB, 17337 packets (not yet analysed) | 0.67 MB |

- **A smaller MSS does not help**: the MTU/fragmentation explanation (H1) is refuted for downloads.
- **Loss grows with packet size, towards both destinations**: larger packets need more radio/transport units, so a path with a per-unit
  loss loses big packets more often. The loss is not specific to DNA; DNA's TCP collapses while Cloudflare's congestion control tolerates it
  (destination dependence via the sender's congestion control, as in M1).
- Each download stopped after 4 194 286 body bytes (5 000 000 requested) in ~23-29 s, cleanly (connection closed by the server). Not seen in
  the good state; unexplained, possibly a server-side limit per connection time or size under slow transfer.
